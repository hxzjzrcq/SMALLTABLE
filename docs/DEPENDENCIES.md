# 依赖与部署约定

本文描述当前源码的依赖用途及运行方式。直接依赖与版本范围以 `package.json` 为准，安装解析结果以 `package-lock.json` 为准；本文不重复维护版本清单，也不代表最新漏洞审计。

## 直接依赖

| 依赖                 | 用途与维护注意                                                     |
| -------------------- | ------------------------------------------------------------------ |
| `react`、`react-dom` | 桌面及内嵌属性工具的界面渲染                                       |
| `express`            | HTTP API、静态页面和素材服务                                       |
| `ws`                 | 房间 WebSocket 同步与连接维护                                      |
| `zod`                | 房间数据、备份和命令校验；浏览器入口使用 jitless 配置              |
| `sharp`              | 上传与恢复图片的检查、转码；带原生组件，需在目标平台安装匹配的依赖 |
| `adm-zip`            | 含图片的房间 ZIP 备份与恢复                                        |
| `@dndroll/core`      | `file:packages/dndroll-core` 本地依赖，不从外部注册表取得规则源码  |

开发依赖分工：`typescript` / `tsx` 用于类型检查、Core 编译及 TypeScript 执行；`vite` / `@vitejs/plugin-react` 用于前端开发和打包；`concurrently` 同时运行开发服务；`jsdom` 提供测试 DOM；`prettier` 负责格式；`@types/*` 提供类型声明。

当前 `npm start` 通过 `tsx` 直接运行服务端 TypeScript，尚无独立服务端 JavaScript 构建。因此生产安装也必须保留开发依赖，不能使用 `npm ci --omit=dev`。如以后改为编译后启动，应同时更新脚本与此约定。

新增依赖前确认现有代码和运行时是否已经覆盖需求；确需引入时说明用途并同步锁文件。依赖更新按影响范围验证：图片/ZIP 涉及上传、恢复和体积限制；网络或校验库涉及协议、权限与连接；前端构建库涉及构建和界面。不复制目标机器以外的 `node_modules` 作为部署依赖。

## 安装、构建与启动

运行环境为 Node.js 22 或更新版本及 npm，命令均在项目根目录执行：

```bash
npm ci
npm run build
npm start
```

`build` 先编译本地 Core，再做 TypeScript 检查和 Vite 前端构建。`start` 只启动服务，不自动构建。`dist/` 是前端产物，不能单独当作完整站点部署；服务端源码、本地 Core 包、配置和依赖同样需要保留。交付包虽含产物，修改源码后仍需重新构建。

开发使用 `npm run dev`，默认访问 `http://127.0.0.1:5173`，由 Vite 代理 API、素材和 WebSocket。生产默认访问 `http://127.0.0.1:3000`，由一个 Node 进程提供全部服务。

## 配置与持久化

服务入口会读取工作目录中的 `.env`，也可由部署环境注入变量。参考 `.env.example`；示例密码必须替换，配置和凭证不进入源码包。

| 变量                                  | 当前行为或默认值                                                         |
| ------------------------------------- | ------------------------------------------------------------------------ |
| `ROOM_PASSWORD`、`DM_PASSWORD`        | 仅首次初始化需要，须符合密码策略且彼此不同；已有凭证时不读取其值作为密码 |
| `HOST`、`PORT`                        | 默认 `127.0.0.1`、`3000`；容器等环境按网络安排设置监听地址与端口         |
| `DATA_DIR`                            | 默认 `./data`，相对工作目录解析；保存 `room.json` 及 `assets/`           |
| `COOKIE_SECURE`                       | 值为 `true` 时为会话 Cookie 添加 Secure；HTTPS 部署应设置                |
| `MAX_SEATS`、`IDLE_MINUTES`           | 默认 15 席、30 分钟无操作离开；席位最多 15                               |
| `MAP_BYTES`、`MAP_PIXELS`、`MAP_EDGE` | 默认 10 MiB、16,000,000 像素、单边 8192 像素                             |
| `TOKEN_BYTES`、`TOKEN_EDGE`           | 默认 128 KiB、单边 256 像素                                              |

棋子上限为 255，私人笔记上限为 65,535 字节；不是上述环境变量配置项。`DNDROLL_URL` 是保留配置，当前属性工具实际加载同源 `/dndroll.html`，不能靠它切换外部工具。

`DATA_DIR` 必须位于可写且重启、重新发布后仍保留的存储上。不能只保存 `room.json` 而丢失 `assets/`。房间完整备份由 DM 导出，含 DM 私有说明；不含密码、连接凭证、玩家私人笔记或本地属性工具数据。迁移服务器时可在停机后单独转移 `credentials.json`，或通过重置命令设置新密码；不要迁移运行锁和临时文件。本机数据由玩家自行转移。

## 密码管理与重置

密码策略由服务端统一执行，初始化、网页修改和重置共用：8–128 个 Unicode 码点；大写英文字母、小写英文字母、数字、特殊符号中至少两类；不含空白和控制字符。特殊符号按 Unicode 标点或符号分类。两种密码不能相同；网页修改的新值不能等于该项旧值。

常见弱密码表在 `src/server/weak-passwords.json`，按完整字符串忽略大小写匹配，不作子串拦截、不访问外部服务。这是小型本地名单，不是穷尽的强度评分。增补名单后重启生效；既有密码不会因名单更新而自动失效。

首次启动：部署者在 `.env` 提供符合策略的初始密码，服务创建凭证文件；也可在启动前执行重置命令直接初始化。示例值不可使用。凭证建立后可从 `.env` 移除两项初始密码，重启和重新发布不会用环境中的旧值覆盖凭证。凭证损坏时拒绝启动，不静默回退到初始密码。

网页操作：DM 工具箱 → 密码管理，再次输入当前 DM 密码，可单改房间口令、单改 DM 密码或同时修改。两项一起修改须全部验证通过并一起保存；保存失败保留原密码和权限。修改房间口令会使所有连接（包括操作者）失效，必须用新口令进入；仅修改 DM 密码保留桌面连接，但撤销所有 DM 授权。接口和解锁共用尝试限流。

忘记密码时，在 CMD、PowerShell 或其他交互终端进入项目目录：

1. 停止 SMALLTABLE 服务；前台运行可按 Ctrl+C，后台运行应停止对应服务。
2. 执行 `npm run password:reset`。
3. 按提示输入并确认两个新密码，输入不回显；Ctrl+C 取消。失败不修改原凭证。
4. 执行 `npm start` 或重新启动后台服务。

重置读取 `.env` 中的 `DATA_DIR`，但不要求知道旧密码；两种密码一起重设。只更新凭证，不改变桌面、素材或私人笔记；也可用于修复损坏的凭证文件。必须在交互式终端运行，不接受命令参数或管道传递密码。

凭证文件保存独立随机盐与 scrypt 哈希，不存明文，不进入桌面快照或 ZIP 备份。程序创建文件时请求仅当前用户可读写的权限；Windows 部署仍应通过目录 ACL 限制访问。

服务和重置命令共用操作系统管理的本机互斥：独占绑定一个由规范化真实数据目录路径生成的回环 TCP 端口（范围 10000–29999，仅 `127.0.0.1`）。该端点不提供管理 API，不需要公网放行，也不新增依赖。即使进程被强制终止，操作系统也会释放互斥，新进程可重新取得；运行中的服务仍阻止重置及同目录重复启动。

端口映射存在碰撞可能；如果另一个数据目录或无关程序恰好占用同一端口，会显示端口号并拒绝启动，不另选端口绕过互斥。需处理占用或在停机后迁移数据目录；HTTP 监听端口不要占用该运行锁端口。同机进程需使用相同网络命名空间与一致的目录视图，不支持跨容器命名空间或跨主机共享数据目录。

从 0.5.5 升级前先停止旧服务，不同时运行不同版本。旧 `credentials.lock` 若含已退出的 PID，新版本会清理；若 PID 仍存在、权限不足或文件内容无法识别，则拒绝启动并提示。PID 被其他进程复用或旧文件损坏时，需人工确认旧服务已停止后只删除旧锁文件。0.5.6 不再创建该锁文件，因此之后的崩溃不会产生此类文件残留。不要删除 `credentials.json` 来触发初始化。

HTTP 端口占用等监听错误会输出原始错误码（如 `EADDRINUSE`），完成服务和互斥清理后以非零状态退出。进程管理器可在原因排除后重试，不会被这次启动遗留的互斥挡住。

## 托管与代理边界

- 当前架构是一套部署、一张桌面、一个 Node 进程。不支持多个实例共享同一数据目录或仅靠负载均衡扩容；会话、房间状态和变更队列都在单进程内存中。
- 托管环境必须支持长驻 Node 进程、WebSocket 和持久化文件系统。仅静态托管或每次请求临时启动的函数环境不能直接承载当前完整服务。
- 反向代理需转发 HTTP 与 `/ws` 的 WebSocket Upgrade，保留浏览器访问的 Host，使服务端同源检查正常。站点按根路径提供；子路径部署尚无适配。
- 公网 HTTPS 可在代理终止 TLS；浏览器使用同源 HTTPS/WSS。设置 `COOKIE_SECURE=true`，确认代理允许持续的 WebSocket 连接。
- 当前限流取实际连接的远端地址，不信任转发头。经过代理后多个玩家可能共用同一限流桶；部署验收需检查多人进入及 DM 解锁，不能仅添加转发头就假定可按玩家区分。
- 进程重启后内存会话和 DM 授权失效，客户端需重新连接或进入；房间数据从持久化目录恢复。停止时应给进程处理 SIGTERM/SIGINT 和保存的时间。
- 仓库不含 Kimi 等平台专用发布适配。平台如需特殊启动或构建流程，应单独说明并验证，不把临时适配隐含进标准命令。

部署验收至少覆盖：外部浏览器进入、两端同步、DM 解锁、图片上传、重启后桌面恢复及备份恢复。构建成功和无头浏览器可见不能单独证明外部用户能够访问。
